# Bug Sweep Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the eight open, already-decided calit bugs — each a small, independently reviewable fix with its own test.

**Architecture:** Eight independent tasks, one bean each, no shared state between them. Each touches one or two files plus a test. Ordered so that a task whose test asserts on text produced by an earlier task runs after it (Task 3 reworded message → Task 4 asserts on it). Nothing here changes the database schema, so there is no Flyway migration in the whole plan.

**Tech Stack:** Quarkus 3.38 / Java 25, Panache entities (public fields, no getters), Qute `@CheckedTemplate` views, RestAssured + `@QuarkusTest` (one reused JVM + one reused Dev Services Postgres), Mockito `@InjectMock` for `CalendarPort`.

**Spec:** the beans themselves — each carries its own analysis and, where one was needed, a recorded decision:
`calit-4whp`, `calit-ek26`, `calit-75vf`, `calit-jk8y`, `calit-w7gq`, `calit-h8mb`, `calit-a4yj`, `calit-mhgs`.
Read a task's bean with `beans show <id>` before starting it. Excluded from this sweep by explicit scope decision: `calit-o69e` (EventGoneException + recreate — its own plan), `calit-mjof` (needs a product answer first), `calit-64hy` (already answered "don't re-resolve"; it dies when `o69e` lands).

## Global Constraints

- **Docker must be running.** `mvn test` boots a Dev Services Postgres. There is no H2 fallback.
- **Build JDK.** `export JAVA_HOME=~/.sdkman/candidates/java/26.0.1-librca` before `./mvnw` — the default `mvn` is JDK 21 and fails with "release 25 not supported".
- **One suite run at a time.** The Dev Services container is reused and `quarkus.flyway.clean-at-start=true` drops the schema at boot; a second concurrent `mvn test` fails with "relation does not exist".
- **Never open a PR while the suite is red.** `mvn test` must be fully green — 0 failures, 0 errors, `BUILD SUCCESS`.
- **i18n parity is mandatory.** Every new or changed `@Message` default needs a matching `key=` line in BOTH `src/main/resources/messages/adm_de.properties` and `adm_he.properties` (or `msg_de`/`msg_he` for the `AppMessages` bundle), in the SAME change. `{placeholder}` names identical across all three.
- **Owner scoping.** Every query filters by `currentOwner.id()`. No task here adds a query that crosses owners.
- **Never edit an applied Flyway migration.** No task here needs one.
- **Formatting gate.** `mvn spotless:check` runs at `verify`. The lefthook pre-commit hook auto-formats staged `*.java`; if you commit outside the hook, run `bun run format` first.
- **Admin user is always id 1** after `DatabaseResetCallback` reseeds. `FormAuth.login()` returns the `quarkus-credential` cookie for it.
- **RestAssured cannot execute JavaScript.** Assert on served HTML and on stable marker comments (`CALIT_TZ_REFORMAT`), never by running the script.
- **Beans discipline.** Set the task's bean to `in-progress` before starting, tick its todo items as you go, add a `## Summary of Changes` section and set `completed` at the end, and include the bean file in the commit.

### Task 1: Coerce an invalid timezone on save (`calit-4whp`)

**Files:**

**Background.** `updateSettings` stores `row.timezone = timezone` straight from the form. The line directly below it already guards `locale` with `AppLocales.isSupported`. **Scope decision — no backfill migration.** The bean's third todo ("consider whether existing rows need a backfill/repair pass") is answered NO. The value can only be set by a hand-crafted POST against your own account, and the guard below repairs any such row the moment it is saved again. A migration that rewrites owner data to fix a self-inflicted, self-repairable, never-observed value is not worth its checksum. Record that answer on the bean.

**Background.** `/me` and `/me/pending` render bookings in the owner's STORED zone (`body[data-tz]`, set by `adminBase.html:22`); `/me/bookings/{id}/manage` renders them in the BROWSER-DETECTED zone, because it passes `Layout.tzBar` so it HAS a `#tz-picker`, and `TZ_SCRIPT` marks the detected zone selected in it (`o.selected = z === detected`). Owner stored in `Europe/Amsterdam`, travelling in Tokyo, booking at 13:00 UTC: the dashboard says 15:00 and the manage page says 22:00, one click apart.

**Decision (recorded on the bean, 2026-08-17): /me standardises on the STORED zone.** The picker becomes an explicit per-page override rather than the default. Availability rules, per-type working hours, date overrides and reminder times are all authored in the stored zone; one zone for authoring and display is the honest model. Whichever zone is on screen stays NAMED on screen.

**Fix shape.** `TZ_SCRIPT` is shared with the invitee pages, which MUST keep auto-detecting (that is the Calendly standard and is not in question here). So the picker's initial selection follows `document.body.dataset.tz || detected` — the exact precedence the no-picker branch of `render()` already uses. Invitee pages emit no `data-tz` (only `adminBase.html` does), so they keep detecting; `/me` pages get the stored zone. One expression, one behaviour, both surfaces.
